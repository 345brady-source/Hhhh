## What the later plans must know

- **The research's "fails" for the refused code was really a wait.** With the page's policy on the worker files the engine never rejects: the refusal is an uncaught failure inside the worker. The vendored start called directly waits for ever. Only `NS.textengine.start()` ends it (through the boot file). Plan 03 must not start the engine any other way.
- `read()` resolves with `[]` for a strip with nothing printed on it **without starting the engine**, so it also resolves there when the engine cannot start. Call `start()` to learn whether the engine runs.
- Reads are taken one at a time in the order asked; the time limit of each counts from its own turn.
- An unknown `mode` is read as a line.
- Errors: `code` is `load`, `time` or `fail`; `message` is a fixed plain text; `detail` is the engine's or the browser's own words, for the console only. A `load` error also has `why`.
- `start()` replaces `window.Worker` for the one synchronous call that makes the engine's worker and puts it back at once; this is how a failed start can end its worker.
- In the refused-code state the engine itself writes two error lines to the browser's console. Nothing reaches a screen.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] A refused start waited the full 20 seconds and came back as the wrong class**
- **Found during:** Task 1, the check's first run (pass 2 red: `code load, why time, after 20001 ms`)
- **Issue:** When the host refuses to prepare the engine's code, the engine reports nothing to the page; the failure is uncaught inside the worker.
- **Fix:** The boot file listens for a failure nothing caught and tells the page; `start()` watches the worker from its first moment and ends the start at once. Also covers failures the engine reports only through its error handler and then never answers.
- **Files:** `assets/vendor/textread/textread-boot.js`, `assets/js/textengine.js`
- **Verification:** pass 2: `load`, `compile`, 312 to 344 ms, twice
- **Commit:** `4842e24`

**2. [Rule 2 - Missing critical] A failed start left its worker running**
- **Found during:** Task 1, writing `start()`
- **Issue:** The engine hands its worker over only once it has started, so a start that fails could not end it; each retry would leave another one holding the language data. The plan's threat T-01.2-06 requires the worker to be released.
- **Fix:** `start()` keeps the worker the engine makes and ends it when the start fails or runs out of time.
- **Verification:** the check counts workers: 1 while started, 0 after `stop()`, 0 after each failed start
- **Commit:** `4842e24`

**3. [Rule 1 - Bug] A blank strip read as a line came back with an invented word**
- **Found during:** Task 1, the check's first run (pass 1 red: `a blank strip read as 1 words`)
- **Issue:** Told that a strip is one line of text, the engine makes a word up when nothing is printed on it. Read as a block it returns nothing.
- **Fix:** A class rule, not a special case: a strip whose lightest and darkest points are nearly alike has nothing printed on it and is not handed to the engine. It also saves the engine's time on every empty strip.
- **Files:** `assets/js/textengine.js`
- **Verification:** pass 1: `blank strip: 0 words as a line [], 0 as a block []`; the drawn line still reads exactly
- **Commit:** `4842e24`

**4. [Rule 2 - Missing critical] The class `file` had no proof, and a missing first file would have been called a refusal**
- **Found during:** Task 1, after the fix above
- **Issue:** The plan's last rule calls any failure that names no file's address `worker`. A worker whose first file cannot be loaded fails with no words at all, so a file left out when publishing the probe would have told the owner "this page is not allowed to start the worker", which is false and would send the phase the wrong way.
- **Fix:** A wordless error at the worker means its first file never ran: class `file`, unless the page's policy was seen refusing that file, then `worker`. The plan's last rule still decides failures that come with words. The check answers each of the reader's two small files 404 once and requires `load`, `file`.
- **Verification:** pass 1: both cases `load`, `file`, 7 and 12 ms, no worker left
- **Commit:** `4842e24`
- **For the orchestrator:** this narrows one sentence of the plan's wording; say so if you want the plan's literal rule instead.

**5. [Rule 3 - Blocking] The probe page is served by the check's own small server, not by an intercepted answer**
- **Found during:** Task 2, the check's first `--probe` run (state 3 red: the page said a file could not be loaded)
- **Issue:** In a frame without allow-same-origin the browser fails every sub-request of a document whose answer was intercepted (`net::ERR_FAILED`), so the page's own stylesheet and module never loaded. The fault was in how the check served the page, not in the page: the portal page, served by a real server in the same frame, loads its files.
- **Fix:** The check serves this checkout on a port of its own with the framed portal page's policy on `reader-probe.html`, and moves the frame there. Same frame, same sandbox, same policy.
- **Files:** `checks/reader-frame.js`
- **Verification:** `--probe` state 3: `load`, `worker`, the right two sentences
- **Commit:** `94a7398`
