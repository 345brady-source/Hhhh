<objective>
Rebuild how the portal reads a subscription agreement so that the fields of each signature block land on the printed
lines, for the right signer, and every placed field says how sure the portal is.

Purpose: wrong placement is the owner's main complaint. A probe run while planning (kept at
`.planning/phases/01-accurate-field-placement/checks/baseline-probe.js`) uploaded two generated agreements through
today's code: 0 of 15 printed blanks got a field on them, one signature box landed on the page title, the firm's column
was given to the investor, and both agreements were saved for onboarding with nobody looking at them.

Output: a new module `assets/js/placement.js`, `autoFields` in `assets/js/esign.js` rebuilt on it, and a repeatable
accuracy measurement over generated agreements.

Why today's placement misplaces fields (read from the code, confirmed by the probe)
1. `autoFields` (esign.js 2647-2724) reads only the last page that carries a signature label (line 2667). The usual
   agreement has the investor's signature page before the firm's acceptance page, so the investor's page is never read
   and the investor gets a fallback block at fixed positions on the last page (2713-2717), on top of whatever is there.
2. Labels are tested against single text runs, not lines (`pageText`, 2608-2633). A run is whatever the PDF producer
   wrote: "By: ______________________________" arrives as one run, so the anchored patterns for name, date and title
   (2635-2637) fail on a line that holds two labels, while the signature pattern (2634) accepts any run that merely
   starts with the word, such as the title "Signature Page to Subscription Agreement".
3. The field is positioned from the label's text box alone (2688-2693): after the end of the run, or under it. Nothing
   looks for the printed line. With underscores inside the run the box lands to the right of the line (probe: line at
   x 92-272, box at x 277-457); with a caption under a drawn line the box lands beside the caption; a drawn line is
   invisible to the code. The width is always the type's default, never the line's.
4. Positions divide the raw text matrix by the page size (2625), ignoring the crop box origin and page rotation that the
   editor and the stamping code honour (`pageFrame`, 526-539).
5. Whose field it is (`ownerOf`, 2670-2679) is the nearest run above, within 30% of the page height, that contains
   words like "the Fund", "Manager" or "member" anywhere in it. Body sentences count as headings, columns are ignored,
   and with countersigning off a firm block is handed to the investor (2678).
6. Nothing records how sure the portal is. The upload form saves the agreement straight away whenever a signature field
   exists (`NS.forms['es-agreement']`, 2850-2853), and so does document intake (`assets/js/intake.js` 457-472), so a
   guess goes live for onboarding unseen.

What the probe measured about reading printed lines (so the thresholds below are grounded)
- Rendering a page at scale 2 and scanning its pixel rows for dark runs finds underscore runs and drawn rules alike,
  with the exact horizontal extent of the printed blank (underscores: x 92-272 found, 92-272 printed).
- An underscore stroke sits about 1.6 pt below the text baseline and is 0.5 pt thick; a drawn 1 px rule is 1 pt thick.
- The same scan also reports short false runs along text baselines (serif feet touching, 16-28 pt long) and the
  underline of an underlined heading. All of them have ink directly above; a blank does not. That is the test to use.
- Cost: about 5-35 ms to render and 20-40 ms to scan a Letter page.
- The browser prints "By: ____" as one text run per printed line.
