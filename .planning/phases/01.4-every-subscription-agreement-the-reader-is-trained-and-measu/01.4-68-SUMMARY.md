# Phase 01.4 Plan 68: PDF fallback for unreadable or picture-only PPMs, read whole Summary

When an uploaded PDF's extracted text cannot be read, the intake now sends the PDF itself to the portal's reading server, which passes it to the reading service as a document. This covers scrambled text layers, and picture-only PDFs when a reading server is set. The request uses the same instructions and the same JSON shape. A PDF over one request's limits is read in page ranges and the answers are merged. Readable documents still send exactly the plan 66 request.

**Nothing was spent.** Every run used fake intakes, with no key. **SCRATCH/blind/ was not opened, listed or used.** Only the public PDFs in SCRATCH/public-agreements were used, plus copies made from them. This is not ready to call working. Plan 67 measures it once on the blind PPM, and then the owner checks it.

## Request shape for the PDF path

- **Browser body:** `{ prompt, pdfs: [{ name, data, pages, of }] }`.
  - `data` is base64 with no line breaks (FileReader.readAsDataURL, the part after the first comma).
  - When the whole document fits in one request, these are the uploaded file's own bytes. The check confirmed the SHA-256 matches the broken file.
- **Prompt:** `instructions()`, a blank line, `DOCUMENTS:`, then the readable documents' `corpus(...).text` if there are any, then one line per unreadable PDF:
  `=== Document: <name> (<M> pages) === attached as a PDF because its text layer could not be read`
  - A range adds ` (pages a to b of M)`.
  - A test cap adds ` (test spend cap: pages 1 to N of M)`.
- **Server message:** one user message. For each PDF it holds a text block `PDF attached: <name> (all M pages | p of its M pages)`, then `{ type: 'document', source: { type: 'base64', media_type: 'application/pdf', data } }`. The prompt follows last as a text block, unchanged.
  - With no PDFs (absent or `[]`), the content is still the prompt string exactly.
  - The free count uses the same messages.
- **Server limits:**
  - At most 5 PDFs, or 413.
  - Each `data` must be base64 whose bytes start with `%PDF-`, or 400.
  - `pages` and `of` must be integers with of ≥ pages ≥ 1, or 400.
  - 600 pages in all, or 413.
  - The body limit is 32 MB (it was 2 MB).
  - With PDFs, the input is always counted first. Over 900000 tokens gets 413 too_large before any call. A failed count gets 402 with a cap and 502 without one.
- **Read log:** adds `pdfs` and `pdfPages`, as numbers only, and only when PDFs were sent. The plan 66 read-log test still passes unchanged.
- **D-36 holds:**
  - With no unreadable PDF, the browser body was `{ prompt }` byte for byte as plan 66 sends it. This was checked on the public RockStep PPM (204305 characters, identical) and on the hedge sample.
  - The only console.js edit is ik-read's filter condition. It keeps a PDF (one with a file and a pdf.js page count) of 40 characters or fewer when `NS.integrations.serverUrl(W())` is set.
  - ik-read's hash in the check is now `b6e0356fd10fd2da`, with the reason comment "plan 68: D-38 routes a picture-only PDF to the PDF path instead of 'No readable text was found'".
  - The other 12 pinned slices are byte-identical (13/13 against the updated table).

## Range size, byte limit and merge rule

- **Limits:** `NS.intake.RANGE_PAGES = 600` and `NS.intake.RANGE_BYTES = 31 * 1024 * 1024`. A request's size is measured as prompt plus base64 plus a small overhead.
- **One request or several:**
  - All unreadable PDFs go in one request when there are at most 5 and their pages together are at most RANGE_PAGES.
  - Otherwise each PDF is cut into consecutive ranges of RANGE_PAGES, each its own request, sent one after another.
- **Halving:** a request over RANGE_BYTES, or answered 413, is split. A request with several PDFs becomes one request per PDF. A single range is cut in half. A 1-page range that is still too large fails with prompt_too_large.
- **Building ranges:** each range is a new PDF of exactly those pages, made with pdf-lib 1.17.1 (load with ignoreEncryption, then create, copyPages and addPage). The library is loaded through intake.js's own loadScript.
- **Prompt and progress:** the readable corpus rides only in the first request. onText keeps counting across requests (checked: 618 of 618 characters).
- **Failures:** any range that fails makes the whole reading fail with that error's code. ik-read's built-in result and today's note follow (checked: "Reading could not finish.").
- **Merge:** `NS.intake.mergeAnswers(answers)` works in range order.
  - A term takes the first non-empty value (null, '', false, [] and {} count as empty), with that same answer's `sources[path]` and `confidence[path]`.
  - Lists are concatenated and de-duplicated, keeping the first entry: classes, structure.feeders and providers.others by name; investorTerms by label (case and spacing ignored); tiers, fees.other and notes by normalized JSON or text.
  - `update` takes the first non-empty value.
  - Source and confidence keys that are not a merged term come from the first answer that has them.
  - On the check's 3 synthetic answers it gives exactly the expected object. On screen, the merged answer reaches review through normalize unchanged.
  - A single answer is returned as is.
- **Production never cuts a document:** `TEST_PAGE_LIMIT` is unset (checked), and every page of the broken PDF was sent in each case.

## Measure part (plan 67's tool)

- **run.json** now also records:
  - `sent`: `pdf`, `text` or null.
  - `ranges`: [[a, b], ...], one per PDF request.
  - `pdfOf`.
  - `testPageLimit`: null unless a test cap applied.
  - `requests`.
  - `attempts`: [{ maxTokens, testPageLimit, outcome, free }].
  - `maxTokens`: the value actually used.
  - All of these come from the request bodies the harness route sees. raw.json is the single answer, or the list of range answers when the document was split.
- **Test-cap fitting:** this runs only after a refusal that cost nothing (402, the log row is spend_cap with a count, and the folder's spend did not change). At most 3 attempts.
  - First, max tokens = (remaining cap − counted tokens scaled to all pages × DEAREST input) ÷ DEAREST output × 0.95. The pages and prices come from model.mjs. This value is used only when it is at least 16000, and the server is restarted with it.
  - Only if that is below 16000: max tokens 16000 and the test-only `NS.intake.TEST_PAGE_LIMIT` set to the most pages that fit (× 0.95). The output says `test spend cap: pages 1 to N of M`.
- **No readable text:** if the screen returns to upload with "No readable text was found", the run stops with `outcome failed, why no-readable-text`.
- **Fake proof on the broken PDF** (fake count of 3000 tokens a page):
  - Cap $2.00: `attempts: 2 (max tokens 64000: refused at no cost; max tokens 30928: read)`, ranges [[1,12]], pdfOf 12, testPageLimit null.
  - Cap $1.00, in pages/: `attempts: 2 (max tokens 64000: refused at no cost; max tokens 16000, test spend cap: pages 1 to 6 of 12: read)`.
  - Cap $0.01 in the first folder: 1 attempt, refused. The built-in profile and the could-not-finish note followed. The cap counted the folder's earlier fake call ($0.5222, fake usage).
- **For plan 67:** the real mode keeps plan 66's proxy retry. The fitting runs inside each try.
